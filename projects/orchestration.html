AGENTS · MCP · OAUTH · WINDOWS

A finished job is not a successful mission.

Connecting a web assistant to real coding agents while keeping execution and goal validation as two distinct operations.

PUBLIC CODEReviewed on 21/10/2026

completed ≠ validated

AT A GLANCE

Challenge

Run multiple AI agents on real tools without granting unrestricted access.

What I built

An MCP gateway, persistent broker and Windows runners with observable jobs.

Evidence

The code is public. Executed work is not automatically a validated mission.

01 / THE ACTUAL PROBLEM

The actual problem

Starting an agent from chat is easy. Giving it carefully scoped access to a personal workstation, detecting stalls and knowing whether the goal was reached are much harder.

Process exit is not a business outcome: code can be wrong, tests can fail and runners can disconnect mid-operation.

02 / HOW IT WORKS

How it works

A web client invokes MCP tools through an OAuth gateway. A VPS broker stores jobs and missions in SQLite. A trusted Windows runner polls outbound for structured work and launches configured agents such as OpenCode or Codex.

Jobs describe a workspace identifier, known runtime, permission mode and goal. There is no arbitrary shell command in the exposed interface; the runner independently validates the configuration and builds fixed argument vectors.

03 / ENGINEERING DECISIONS

Engineering decisions

1. Split control and execution planes: broker state is independent of the workstation. 2. Guard concurrent transitions using session epochs and compare-and-set rules. 3. Keep bounded logs and events for diagnosis rather than indefinite raw transcripts.

The core contract: a completed job means the process exited with code 0. Its mission still needs independent validation before being labelled successful.

04 / A REAL FAILURE MODE

A real failure mode

A runner can vanish after launching work. Blind retry could duplicate a write or deployment. The broker marks such a job lost instead of claiming success or replaying the action. Prolonged inactivity is reported as a suspected stall, not treated as permission for automatic destructive intervention.

05 / EVIDENCE AND LIMITATIONS

Evidence and limitations

The public repository documents the broker, policies, state machine and tests. The existing Excalidraw image is illustrative. Implemented controls reduce risk; they do not guarantee flawless security or prove completion of any specific user's objective.

06 / ENGINEERING

Three choices that matter

Least privilege

Typed MCP tools, allowlisted workspaces and fixed runtime invocations.

Honest outcomes

Execution and validation have separate states and APIs.

No blind replay

Lost jobs are neither successful nor automatically retried.

07 / NEXT

What remains to be proven

EXPLICIT LIMITS

A serious integration test should probe disconnects, write idempotency, broker state and objective-validation criteria.
