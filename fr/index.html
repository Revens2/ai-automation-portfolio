01
RAG · SYSTÈMES DE CONNAISSANCES

Une couche de connaissances privées pour plusieurs agents IA

Rechercher, ingérer et réutiliser des connaissances sans confondre index et source de vérité.

Code public

Problème

Les notes et conversations accumulées sont difficiles à retrouver, faciles à dupliquer et risquées à transmettre intégralement à un LLM.

Réalisation

vault-mcp fournit une recherche hybride lexicale/vectorielle avec fusion par rang réciproque et graphe de notes ; llm-wiki structure les contenus bruts ; convia-sanitize sépare la rédaction des secrets et la publication vers le RAG.

Contrôles et limites

Intentions d'écriture soumises à consentement, gestion des conflits, traitements incrémentaux, ingestion tolérante aux quotas, contrôles reproductibles. La rédaction réduit les risques sans garantir une anonymisation parfaite.

Limites connues

L'architecture de production évolue ; la documentation RAG publique ne constitue pas un instantané unique du déploiement actuel.

02
REVUE DE CODE · QUALITÉ RAG · ANALYSE PRODUIT

Des audits qui séparent les preuves des hypothèses

Même exigence dans trois domaines : ce qui a été vérifié, ce qui échoue et ce qu'on ignore.

Code public

Problème

Une revue qui transforme silencieusement une absence de données en succès donne une fausse confiance.

Réalisation

pr-reviewer exécute des revues sémantiques de PR isolées et en lecture seule, avec statuts GitHub consultatifs. llm-wiki intègre un lint RAG fondé sur des règles (R1–R24). Les rapports SEO de Watchy croisent les signaux GA4/GSC disponibles et documentent leurs lacunes.

Contrôles et limites

CI déterministe indépendante de l'analyse sémantique ; certification du modèle exigée avant PASS ; données SEO incomplètes signalées comme telles.

Limites connues

La revue de PR est consultative : elle ne bloque pas les fusions. Rapports SEO et analytics Watchy privés ; aucun chiffre de performance inventé.

03
AGENTS · MCP · PERMISSIONS

Piloter de vrais agents de code avec des outils MCP bornés

Un assistant web peut lancer, suivre et gérer des missions d'agents sans obtenir un shell distant généraliste.

Code public

Problème

Les agents doivent agir sur des machines de développement, sans exposer un accès système arbitraire.

Réalisation

agent-orchestrator-mcp relie un client MCP web, une passerelle OAuth, un broker VPS et un runner Windows pilotant les moteurs d'agents configurés.

Contrôles et limites

Cycle de mission structuré, espaces et moteurs autorisés, construction figée des arguments, revalidation côté runner et permissions d'outils restreintes.

Limites connues

Ces mécanismes sont des garde-fous implémentés, pas une promesse de sécurité absolue.

INGÉNIERIE DU CONTEXTE

La fenêtre de contexte est un budget, pas une base de connaissances.

Il s'agit d'une méthode appliquée aux projets d'agents, pas d'un produit indépendant avec des gains en tokens publiquement mesurés.

Méthode de travail : aucun gain chiffré de performance ou de qualité du retrieval n'est revendiqué.

  1. 01

    Récupérer avec précision

    Rechercher selon la tâche et identifier les sources pertinentes au lieu d'injecter des dossiers ou transcriptions entiers.

  2. 02

    Définir les sources d'autorité

    Les notes durables et le code versionné font référence. Un résultat RAG est un index, pas une preuve indépendante.

  3. 03

    Transmettre des relais compacts

    Faire circuler décisions, contraintes, état et prochaines étapes entre agents, pas l'historique complet des conversations.

  4. 04

    Auditer l'incertitude

    Qualifier observations, hypothèses, données périmées et mesures absentes avant de valider une action ou un rapport.
