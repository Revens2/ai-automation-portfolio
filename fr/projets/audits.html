01 / POURQUOI DES AUDITS INDÉPENDANTS

Pourquoi des audits indépendants

Un agent peut considérer un changement comme terminé alors que sa qualité n'a pas été contrôlée. Un moteur de recherche peut échouer alors que l'application semble accessible. Un corpus RAG peut s'indexer sans être cohérent. Les audits servent à confronter ces signaux, pas à produire un feu vert artificiel.

02 / PREMIER CAS : REVIEWER SÉMANTIQUE DE PR

Premier cas : reviewer sémantique de PR

Le projet public pr-reviewer surveille les PR de dépôts explicitement autorisés. Un poller détecte les révisions, une file déduplique par dépôt/PR/commit, puis un worker prépare un snapshot du code en lecture seule dans un conteneur Docker isolé.

Le modèle produit un verdict structuré. Un PASS exige une identité de modèle certifiée. En cas d'échec ou d'incertitude, le résultat n'est jamais converti silencieusement en succès. Le statut GitHub reste CONSULTATIF : aucune règle de protection de branche ne repose uniquement sur cette revue.

La revue sémantique ne remplace pas l'analyse déterministe : tests, Semgrep et Gitleaks gardent leurs rôles distincts. Le code issu d'une PR est une entrée non fiable, jamais une instruction à suivre par le reviewer.

03 / DEUXIÈME CAS : VÉRIFIER UN WIKI RAG

Deuxième cas : vérifier un wiki RAG

Le dépôt public llm-wiki contient un lint de qualité sur un ensemble de règles R1 à R24 : structure, cohérence et références. L'ingestion incrémentale doit respecter les quotas LLM et permettre des reprises, tout en rendant visibles les écarts. Un index « construit » ne signifie donc pas que les connaissances qu'il contient sont correctes.

04 / TROISIÈME CAS : L'ENQUÊTE SEO DE WATCHY

Troisième cas : l'enquête SEO de Watchy

Les audits internes croisent Search Console, GA4, les réponses HTTP et les traces de changements. Un rapport du 21 octobre observait une différence entre l'état d'une lecture Google de sitemap et des requêtes récentes réussies depuis un navigateur. Il documentait aussi explicitement les périodes incompatibles et les données indisponibles.

Ce cas n'est pas une preuve de correctif : l'origine du problème restait inconnue. Le but était de produire une liste d'hypothèses testables et une hiérarchie de risques, pas une explication inventée.

05 / COMMENT JE CONCLUS

Comment je conclus

Chaque audit devrait aboutir à quatre colonnes intellectuelles : constat directement observé, inférence plausible, preuve encore nécessaire et action prioritaire. Un défaut de source ou d'accès est annoncé plutôt que présenté comme une valeur nulle.

Pour les systèmes critiques, la qualité d'un audit se juge à la traçabilité de ses preuves et aux décisions qu'il permet, pas au nombre de problèmes que l'IA prétend avoir trouvés.

06 / DECISIONS

Trois choix qui guident l'audit

Confiance limitée

Le modèle est un reviewer consultatif, sans privilège d'écriture sur le dépôt analysé.

Couches complémentaires

Contrôles déterministes, revue IA et vérifications externes ne se remplacent pas.

Inconnues visibles

Une mesure absente est « non mesurée », jamais « zéro » ni « validée ».

07 / LIMITS

Les limites à ne pas masquer

TRANSPARENCY / 2026-10-21

Aucune métrique de performance des audits ou taux de détection n'est revendiquée. Les rapports Watchy sont privés. Un statut advisory ne bloque pas une fusion et un lint syntaxique ne certifie pas la vérité du corpus.
